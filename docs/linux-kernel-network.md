# Linux kernel network flow telemetry

`linux-network-flow-summary` is an optional Linux x86_64 L3 source for correlating retained TCP/UDP network activity with the process that caused it. It is disabled by default. Enrollment, a requested coverage level, missing evidence, or installation alone cannot enable it.

## Evidence and privacy boundary

The fixed embedded eBPF object observes IPv4/IPv6 TCP/UDP cgroup traffic at the host cgroup-v2 root. It retains only the local/remote tuple, protocol, direction, packet count, SKB-length byte count, TCP flags, PID, fixed 16-byte kernel task name, UID when available at an owner hook, interval times, attribution basis, and explicit parser/map/ring loss counters. Cgroup-SKB execution context is never treated as a process owner; attribution comes from the recent bounded socket-owner map populated by connect, bind, send/receive, sock-ops, and socket-state hooks. When an owner hook supplies a PID, the unprivileged agent may derive the public boot-scoped `process_instance_id` only after matching two bounded procfs identity reads around enrichment; exit, reuse/race, permission, invalid-text, boot-identity, or enrichment-cap cases retain a null identity with an explicit status. It may also fill a missing UID from bounded `/proc/<pid>/status`; the sanitized kernel task name is the process-image fallback when procfs executable/command-line access is unavailable. It never copies application payload; it does not parse DNS, TLS, HTTP, process environment, process memory, file content, Unix sockets, or ICMP. The helper cannot open raw/packet sockets and cannot load a caller-selected object or pin programs/maps in bpffs.

Packet counts are cgroup SKB observations and byte counts are SKB lengths. GSO/GRO, segmentation, retransmission, offload, namespace/cgroup placement, non-initial IP fragments, ESP or excessive/malformed IPv6 extension chains, process exit/reuse, and pressure mean these are not wire-accurate accounting. The parser reads from the kernel network-header origin and walks at most four hop-by-hop, routing, first-fragment, AH, destination, or mobility headers before TCP/UDP; every other target-traffic omission remains an explicit loss counter. Process attribution is exact to the current kernel task when available, otherwise a recent full/local/remote socket-owner association no older than 60 seconds; procfs executable/command-line and process-instance enrichment is best-effort, sanitizer-bounded, explicitly racy, and never exact execution evidence.

## Privileged boundary

The main `challenger-siem` agent gains no capability. A separate locked, non-login `challenger-siem-ebpf` account runs only `Challenger.Siem.EbpfHelper` with exactly:

- `CAP_BPF`
- `CAP_PERFMON`
- `CAP_NET_ADMIN`

`CAP_SYS_ADMIN`, `CAP_NET_RAW`, root execution, writable product state, arbitrary BPF paths, and bpffs pinning are not permitted. systemd creates a mode-0660 `SOCK_SEQPACKET` endpoint owned by the helper and the `challenger-siem` group beneath a non-writable `root:root` directory. The helper verifies the connecting agent UID. The agent validates the exact non-symlink permission profile and accepts only the dedicated helper UID for a direct peer or PID 1/root attested as systemd for the socket-activated listener, then enforces the fixed hello. Frames have a 16-KiB maximum, a fixed property allowlist, helper epoch and monotonic sequence, and strict hello/capacity/privacy constants.

The fixed hook catalog covers socket creation, IPv4/IPv6 bind/connect/sendmsg/recvmsg, TCP sock-ops establishment, accepted/closed TCP socket-state raw tracepoints, and cgroup ingress/egress. Every cgroup program uses an additive BPF link, so stopping or killing the helper detaches it without replacing a pre-existing attachment; the helper rejects a missing, additional, renamed, or re-sectioned embedded program before attachment. All programs are observational and return allow/pass results; they do not replace policy or block traffic.

The kernel maps are bounded at 262,144 flow rows and 32,768 owner rows, with a 32-MiB notice ring sized above the maximum aligned notice footprint of a full flow map. Helper protocol v3 transfers at most 32,768 kernel flow rows every second into a separate 524,288-entry accumulator, for a hard maximum of 327,680 transfers per ten-second health interval. It emits at most 4,096 `network_flow_started`, 60-second `network_flow_sample`, or FIN/RST/inactivity `network_flow_closed` records followed by one sequenced no-payload health frame per interval. A flow already closed before its first output produces one complete closure record rather than separate start and close records, and close work is prioritized over starts and active samples. The agent receives and validates the complete output through the health delimiter before procfs enrichment. Enrichment is cached per PID/UID/kernel-command/attribution-basis/interval identity and limited to 256 unique identities per drain; further identities retain sanitized kernel task/UID attribution without extra procfs reads and report `enrichment_limit_reached`. Original frame order within each priority class, one event per emitted frame, and racy/partial attribution labels remain explicit. The fixed helper service retains its least-privilege capability and syscall boundary and raises only its bounded memory ceiling from 128 MiB to 192 MiB for these fixed maps and accumulator.

Before the first queue write, the agent durably reserves the output's complete agent-sequence range without advancing its collected checkpoint. It partitions events into transactions of at most 100 events or 1 MiB and, after each successful transaction, atomically finalizes the collected/helper/health state for that committed prefix. An interrupted reserved suffix is abandoned exactly once, is never reused, and remains an explicit active gap; already committed queue rows, acknowledged rows, and cumulative helper-loss evidence remain intact. Bounded source health reports output count/bytes/enrichment/timing, native transfer pressure, current/high-water helper occupancy, current/high-water pending output, and the two split exhaustion counters. State schema 3 retains raw per-helper-epoch counter snapshots and adds only deltas to agent-lifetime totals. A helper restart under collector v4 or later therefore cannot move a published cumulative counter backward. `flow_map_full` remains the saturating aggregate of the two loss counters plus any legacy unclassified total. Capacity fields are fixed bounds, not measured historical occupancy; kernel or helper pending backlog is delayed evidence and degrades current health without incrementing loss. An earlier rollback collector ignores the additive diagnostics; retained server evidence remains authoritative, and any backward current-counter movement is a rollback discontinuity and stop gate rather than a reason to edit state.

Delivery remains sequential and bounded: a full 100-event outbound batch is followed by a 100-millisecond backlog delay, while a partial or empty batch returns to the five-second idle cadence. This preserves the existing request-size bound and sequential acknowledgement semantics while providing headroom above the 4,096-record-per-ten-second helper output ceiling. The agent reserves one maximum 4,096-record output and stops consuming before the configured 20,000-row pause boundary so journal, heartbeat, and delivery remain higher priority. Queue insertion precedes collected-checkpoint persistence; accepted/duplicate server acknowledgement precedes acknowledged-checkpoint persistence. Sequence gaps, newly increased map/parser/ring/IPC counters, helper restarts/connections, queue pressure, kernel-drain backlog, helper pending backlog, and stale helper contact remain explicit. Three consecutive clean health frames clear active loss without erasing cumulative counters. Owner misses remain a separate partial-attribution counter because they do not lose the underlying flow observation.

## Signed plan and activation

Build/publish the candidate agent first. Put a private Ed25519 signing key only in ignored operator storage and derive a separate public key. Never put the private key, real configuration, bundle, or validation output in Git.

1. Publish the candidate agent, build the fixed helper, and calculate the helper file SHA-256 and the Ed25519 public-key DER SHA-256. Put the lowercase `sha256:` values in `ApprovedHelperSha256` and `ApprovedSignerPublicKeySha256`; leave `ApprovedPlanHash` empty and set `Enabled=true` only for plan generation.
2. Run the candidate agent with `--kernel-network-plan`, put that exact hash in `ApprovedPlanHash`, and rebuild the plan. The plan hash binds the approved helper and signer hashes as well as every path, limit, version, privacy boundary, and queue threshold.
3. Build a signed bundle with `scripts/build-kernel-network-bundle.sh OUTPUT AGENT_BINARY PRIVATE_KEY PUBLIC_KEY PLAN_HASH`. The lifecycle preflight rejects a signed helper or signer whose hash differs from either the configuration or the candidate plan, and requires the manifest's helper and collector versions to match the candidate agent. Collector identity `linux-network-flow-summary-v5` uses unchanged helper protocol v3 and retains event schema v1. Its bounded stable-procfs identity enrichment invalidates the prior kernel plan and requires a newly signed manifest, but does not replace the native helper or change its attachments, capabilities, maps, or payload boundary.
4. Run `scripts/kernel-network.sh plan --bundle ... --config ... --public-key ...` and review the signed file hashes, signer fingerprint, three capabilities, attachments, service impact, and rollback.
5. After explicit staging approval, run `enable`. It validates or creates only the dedicated locked helper identity, installs the fixed helper/units/agent ordering profile/trusted public key, reloads systemd, and starts the socket. It does not restart an already running helper or the agent.
6. Activation requires separate approval for the exact target/window. When moving from collector v4/helper v3 to collector v5/helper v3 with the exact same approved helper hash, stage the newly signed compatible bundle and restart only the agent; do not restart or detach the unchanged helper. Any helper artifact/hash change instead requires the coordinated agent stop, helper restart/detach, and agent start boundary. Then run `validate` and the live acceptance checks below. Staging or disposable-VM success does not authorize this protected-host step.

The helper dynamically requires `libbpf.so.1`, libelf, zlib, cgroup v2, and readable kernel BTF. An endpoint compiler is not used. The initial native helper supports x86_64; ARM64 agents continue operating with this source reported unsupported.

## Validation

Run `tests/kernel-network-lifecycle/run.sh` for a synthetic isolated-root test of single-file publication, Ed25519 manifest/hash binding, plan/config agreement, fixed file staging, tamper rejection, and rollback preservation. This test does not start services, attach BPF programs, create identities, or use real credentials.

Validate in an approved disposable VM before a protected host:

- signed manifest, exact installed hashes, locked identities, mode/ownership, and no symlinks;
- configured and effective helper capabilities equal only the three approved values;
- the fixed cgroup links coexist with existing programs, and stop removes them without leftover Challenger SIEM bpffs pins;
- synthetic TCP and no-application-payload UDP flows produce cited `network_flow_started`, 60-second `network_flow_sample`, and FIN/RST or inactivity `network_flow_closed` evidence with direction, tuple, PID/process metadata, interval counters, `payload_capture=false`, and healthy source evidence;
- malformed/oversized/duplicate/unknown IPC fields are rejected; wrong peers cannot connect;
- flow pressure, parser omissions, helper/agent/backend restart, queue pause/drain, and server rejection produce explicit loss/health state without silent checkpoint advancement;
- REST `/api/v2/network/activity`, `/ui/traffic`, and `siem_search_network_activity` return the same retained event citation; MCP does not create or update the geolocation cache.

For the collector-v2 patch, use an authorized disposable Linux x86_64 VM and a bounded synthetic workload that reaches 500 flow records per ten-second drain for at least 30 minutes. Acceptance requires average agent writes below 1,048,576 bytes/second; average CPU below 2%, p95 CPU below 5%, and RSS below 250 MiB; normal queue pressure with age below 30 seconds and no sustained growth; acknowledgement gap returning to zero; and no poison/drop increase, helper connection failure, new sequence gap, parser/ring/map/IPC loss, crash, or restart. API/database reads must remain available, and strict L4 must remain healthy after warm-up for one additional complete rolling window.

For collector v4 or v5 with helper v3, use an authorized disposable Linux x86_64 VM with a bounded incident-shaped workload. Produce at least 120,000 measured distinct short-lived TCP flow keys within one ten-second interval without exceeding 262,144 simultaneously resident keys, then stop the burst and require pending helper backlog to return to zero within six minutes. Follow with at least 30 minutes at no more than 18,000 newly closed keys per minute. Require zero increase in kernel-map, helper-table, parser, ring, or IPC loss, explicit backlog while pending work exists, no false-healthy interval, the fixed 4,096-record output ceiling, queue age below 30 seconds without sustained growth, acknowledgement gap returning to zero, zero poison/drop/backoff, the existing CPU/RSS/write SLOs, available API/database reads, and strict L4 healthy after warm-up for one additional complete rolling window. Collector v5 validation must additionally exercise stable identity, PID reuse, exit/race, invalid-text, boot-identity, permission, and enrichment-cap outcomes without false identity or command-causality claims. Separately exceed the documented envelope only in the disposable VM to prove bounded loss/backlog reporting and recovery; finite buffers cannot claim lossless capture for arbitrary unbounded traffic, and any overload loss remains real evidence that cannot be reset or reconstructed.

For any new protected-host rollout, first perform the read-only incident review in [Runbooks](runbooks.md). A collector-v5 canary requires a newly signed bundle, refreshed kernel plan and L4 plan/baseline approvals, exact rollback copies of the prior signed helper/agent bundle and protected configuration, and explicit agent activation and rollback authority. Follow with the documented 24-hour read-only soak, and stop/roll back on either split loss counter increasing, persistent backlog, an SLO breach, unexpected helper discontinuity, queue growth, silent loss, host impact, false process-identity certainty, or inability to restore the prior artifacts while preserving queue and state.

Current sanitized status (2026-08-04): the exact 2.8.1 single-host development deployment passed the initial agent-only acceptance window and one additional complete healthy L4 rolling window. The queue remained bounded, acknowledgements caught up, active loss cleared without resetting cumulative historical gaps, the unchanged helper remained continuous, and the API/database read path remained available. The 24-hour read-only soak is in progress; this short result is not a broader production-readiness claim.

For an explicitly designated single-host development deployment, the operator may avoid a persistent external signer by generating a one-use Ed25519 key only in a root-owned mode-0700 directory under `/run`. A same-helper collector-v5 agent-only build may set `CHALLENGER_SIEM_FIXED_HELPER_BINARY` to the exact installed regular helper. Complete the normal manifest/candidate/config validation, install only the public key, and permanently destroy the private key and temporary signer directory immediately after staging. This workflow does not permit an unsigned bundle, weaker manifest checks, a persistent endpoint private key, reuse of an old approval, or an unapproved helper replacement/restart; every candidate still needs fresh kernel and L4 plan/baseline approval plus rollback copies.

## Rollback

For an agent-only collector-v2 canary rollback, restore the exact prior agent artifact and protected configuration and restart only the agent; preserve queue, WAL/SHM, credentials, checkpoints, source state, helper process, helper attachments, and server evidence. Do not restart or replace the unchanged helper.

For a collector-v5/helper-v3 rollback to collector v4 with the exact same helper hash, restore the exact prior agent artifact, signed manifest/public key, and protected configuration and restart only the agent. Preserve queue, WAL/SHM, credentials, checkpoints, source state, helper process/attachments, and server evidence. Do not delete state or restart the unchanged helper merely to clear identity-enrichment uncertainty.

For a collector-v4/helper-v3 rollback, use the separately approved coordinated window to restore the exact prior signed helper/agent artifacts and protected configuration. Stop the candidate agent, restore and restart the prior helper so its links are recreated from the reviewed object, then restore/start the compatible prior agent. Preserve queue, WAL/SHM, credentials, checkpoints, source state, and server evidence. Validate exact hashes, helper epoch/restart accounting, link cleanup/recreation, source recovery, delivery, and strict L4; never delete or edit state to hide the transition.

Full source removal is a separate operation: disable the source in configuration and restart only the agent, then run the lifecycle `disable` command. It stops the socket/service (detaching links), removes only the fixed helper files/units/profile/trusted public key, reloads systemd, and preserves agent configuration, queue, credentials, source state, server evidence, and the locked helper identity. Verify that no Challenger SIEM cgroup links or bpffs pins remain and that the other agent sources continue reporting normally.
