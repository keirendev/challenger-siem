## Change/rollback boundaries

- Repository changes affect only project code, tests, schemas/contracts when explicitly listed, and public synthetic documentation.
- The disposable VM affects only its exact libvirt domain, exact qcow2 volume, and ignored VM evidence. Recovery is the clean baseline snapshot or recreation; teardown must verify exact targets first.
- The protected-host 2.x retry was subsequently approved and completed through a parallel fresh-database cutover. The v2 database is the active writer; the retained v1 database remains a separate read-only rollback/validation asset. No in-place 1.x schema migration was attempted.
- The operator explicitly approved the current journal scope, live L2/L3/L4 activation, the optional 2.4.0 cross-user executable-visibility profile, the signed kernel-network source, and the 2.8.1 single-host collector-v2 agent update. Exact self-integrity, passive/socket-ownership/process-visibility, kernel-helper/signing/IPC/batching, posture-baseline, audit, and L4 approvals remain configuration-bound; changing their inputs invalidates approval rather than silently broadening collection. The main-agent one-capability profile and helper exact three-capability profile are separately scoped, monitored by self-integrity, and removed through their separately reviewed rollback paths.
- The 2.8.1 rollback boundary is agent-only: restore the exact prior agent artifact and configuration, restart only the agent, and preserve queue, WAL/SHM, credentials, checkpoints, collector state, helper process/attachments, and server evidence. Full helper/source removal remains a different separately reviewed operation.
- The 2.9.0 rollback set separately preserves the previous API drop-in/payload and the previous agent payload/protected configuration/unit. API rollback restarts only the user API; agent rollback restarts only the agent. Both preserve queue, WAL/SHM, checkpoints, package/L4 state, credentials, retained evidence, and the unchanged helper.
- The guest-only `systemd-journal` membership and private test CA were removed during uninstall verification and were absent after snapshot revert. No host trust store, group, ACL, journal setting, or certificate was changed.
- The protected-host canary trusted its one-day test certificate only through the foreground process environment. It did not install a CA, write a unit, emit a synthetic journal message, restart the installed agent, or alter journal visibility. Its exact API and PostgreSQL processes were stopped after the queue drained.
- The later lifecycle attempt reused the already installed private CA and approved agent configuration; it did not alter the host trust store or print credentials. The failed candidate queue and rollback archives remain only in ignored, access-restricted evidence. Because the v2 backend never accepted the candidate's records, that short candidate collection window is retained as an explicit delivery gap rather than silently discarded or converted for v1.

Stop and roll back on privacy leakage, unauthorized mutation, host impact, boot/network/authentication regression, queue/state corruption, silent loss, uncontrolled growth, false-healthy coverage, or inability to recover the guest.
